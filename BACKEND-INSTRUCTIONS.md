# Backend instructions

> Ответ команды бэка на frontend-аудит от 11.11.2026.
> Актуальная ветка с бэкенд-фиксами: `fix/backend-fixes-9` (влита в `develop`
> и в текущую ветку через merge). `app/` и `config/` на фронте не меняются.

## Что уже исправлено на бэке в `fix/backend-fixes-9`

- **B-09. Блокировка пользователей.**
  - `POST /api/users/{userId}/block` — заблокировать.
  - `DELETE /api/users/{userId}/block` — разблокировать.
  - `GET /api/system/users` отдаёт `isBlocked`, `isVerified` и роли.
  - При блокировке сбрасываются сессии пользователя.

- **B-20. Регистрация.** `AuthController::register()` исправлен: корректно
  разбирает `[$token, $userId]` и передаёт e-mail в `startVerification()`.

- **B-21. Контент статьи.** Убран fatal в `VersionedContentData`;
  `GET /api/articles/{id}/content` и `PUT` с `If-Match` работают.

- **B-A2-01. Пустые поля публикации.** Бэк принимает пустые строки для
  `description` и `authorNotes` (ограничение только по максимальной длине).

- **B-A2-02. Пользователь в читалке.** `BooksController::read()` передаёт
  `user` во view `book/book-read`.

- **B-A2-03. Роли в списке пользователей.** `GET /api/system/users` с
  `include=roles` отдаёт роли вместе с пользователями — отдельные запросы
  ролей для каждой строки не нужны.

## Решения бэка по спорным пунктам

- **B-10. Жалобы не делаем.** API и раздел жалоб не планируются. На фронте
  не нужно реализовывать report-модалку, админ-страницу жалоб и пункты
  «Пожаловаться».

- **B-04. `contentData` отдаётся отдельным запросом.** Размер контента может
  быть большим, поэтому текст статьи не включается в read-модель. Фронт
  загружает его через `GET /api/articles/{id}/content` тогда, когда он нужен
  (при чтении). Для отрывка из книги в ответе есть `bookData` с
  `redirectUrl`/`pageStart`.

- **B-11. Смена пароля — через e-mail.** Отдельный роут/страница смены пароля
  не нужны: используется уже существующий сброс пароля по e-mail, как на
  странице логина. Если переход идёт из сайдбара, достаточно поменять
  ссылку возврата (например, «Back to feed» вместо «Back to sign in»).

- **B-14. 404 для несуществующей публикации.** Оставляем как есть: текущее
  поведение немного неидеально, но на сценарии не влияет.

- **B-16. Seed-данные не вернутся.** `SEED_TEST_DATA` и `test_data.sql` не
  восстанавливаем; ссылки на seed в документации не нужны.

- **B-17. Права и счётчики дашборда.** Всё работает: права текущего
  пользователя передаются через сайдбар, дополнительные данные можно
  получить через API. Счётчики дашборду не требуются.

- **B-A2-01. Создание публикации.** На создании бэку нужны все поля; если
  поле пустое — передавайте пустую строку.

- **B-A2-03. Список пользователей в админке.** Используйте system users с
  `include=roles`; роли придут в том же ответе.

- **B-A2-04. Право Publish.** Публикация — это изменение статуса
  (метаинформация), поэтому требуется только `updateMeta`. Расширять право
  до `updateMeta || updateContent` не нужно.

## Короткий чек-лист для фронта

- Не добавлять жалобы и связанный UI.
- Текст статьи/отрывка загружать лениво из API контента.
- Для смены пароля вести на e-mail-сброс.
- Не рассчитывать на seed-данные.
- Пользователей в админке брать из `GET /api/system/users?include=roles`.
- Публикацию проверять по `updateMeta`.
- Пустые `description`/`authorNotes` отправлять пустыми строками.
- Для блокировки/разблокировки использовать `POST`/`DELETE /api/users/{id}/block`.
